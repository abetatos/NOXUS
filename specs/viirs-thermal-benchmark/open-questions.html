Q1VNF download endpoint, file format, auth requirement, and per-night volumeNon-blocking
Question
What is the exact VNF (EOG / CSM) download endpoint and per-night file format, does it require authentication or registration, and what is the per-night (hence full-era) data volume over an AOI-sized filter?
Why it matters
Drives the acquisition client, the batching/budget strategy, and whether an env-var credential is needed at all.
Blocking
No
Default assumption if not answered
VNF per-night CSV, free bulk, no auth (or lightweight registration); filter to the AOI client-side. Resolve at T1: fetch a small window, measure volume/fields/coverage, record go/no-go (REQ-000, ERR-004).
T1 partial finding (2026-07-12, implementer offline probe)
The keyless default is contradicted. A live GET of the defaulted path https://eogdata.mines.edu/wwwdata/viirs_products/vnf/<YYYY>/VNF_npp_d<YYYYMMDD>_noaa_v30.csv.gz returns HTTP 200 with an HTML Keycloak login page (content-type: text/html, ~8.5 KB), i.e. the EOG host is behind SSO — VNF is not keyless at this path. VnfFetcher now detects the login/HTML body and raises a clear ViirsAuthError rather than a CSV parser error. Still unknown (developer T1): the exact authenticated download URL/filename, whether an EOG account + token (or the eogdata auth token endpoint) is required, the true per-night file format/volume, and full-era coverage. Gate outcome: blocked-on-live-run — needs an authenticated VNF fetch. The offline code path (clip/persist/manifest/probe/join/triangulation) is complete and unit-tested; the go/no-go cannot be finalised until an authenticated slice is fetched. Command to complete: uv run noxus fetch-viirs --probe --source vnf once EOG auth is wired (and, for the FIRMS cross-check, FIRMS_MAP_KEY set in .env then uv run noxus fetch-viirs --probe --source firms).
